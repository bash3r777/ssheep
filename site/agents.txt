# ssheep — notes for agents
#
# Version: early prototype. NOT SECURE. No audit, no security review, protocol
# still changing. Do not use for anything important.
#
# This file is the machine-readable version of https://ssheep.xyz — enough for an
# agent to operate a flock without reading prose.

WHAT IT IS
  Control machines ("sheep") from a machine you hold ("the master") through a
  blind relay ("a connector").
  - A sheep only ever dials OUT, so it needs no open port and no public address.
  - Everything between master and sheep is end-to-end encrypted (X25519 + AES-GCM).
    A connector forwards ciphertext it cannot read and cannot forge.
  - The flock is defined by a small signed file (the roster). The only secret is
    the flock key, which signs rosters and is needed only to add or remove a machine.
  - One machine can be in MANY flocks, each with its own key and roster, and a
    relay and a connector can serve several flocks at once.

INSTALL
  curl -fsSL https://ssheep.xyz/install.sh | sh
  # alternatives:
  #   download: https://github.com/bash3r777/ssheep/releases/latest
  #   source:   git clone https://github.com/bash3r777/ssheep && cd ssheep && make build
  # static binaries, linux/darwin/windows, amd64/arm64. no other dependencies.

SETUP — ONE COMMAND, THEN ONE LINE PER MACHINE
  1. on the machine you control from (the "master"):
       ssheep master flock "myflock"
     This creates the flock, pre-adds the project's public relay, mints tickets,
     and prints one line per machine, in three groups:
       🐑 sheep       a machine you manage
       📡 connector   the machine with a public address
       👑 master      a second master; carries the flock key (one minted by default)
     It also reports the flock and accepts any connector that has registered.

  2. paste each line as printed:
       curl -fsSL https://ssheep.xyz/install.sh | sh -s -- --ticket "<ticket>"
     The installer joins the machine itself, by the full path it just installed to,
     so it works whether or not that directory is on PATH. The ticket says what the
     machine is to be, so there is no verb to get wrong and no second command.

  3. on the master:
       ssheep master "myflock" --watch 3m   <- optional: watch machines join
       ssheep see                           <- all flocks, live
       ssheep run "myflock" -- uptime

  Opinionated defaults, all overridable:
    public relay    relay.ssheep.xyz:7000, pre-added to the roster --relay / --private
    tickets minted  3 sheep, 1 connector                          --sheep N / --connector N
    spare masters   1 (a master ticket carries the flock key)     --masters N
    connector port  7000                                          --port

MULTIPLE FLOCKS
  A machine can be in as many flocks as you like, and holds a SEPARATE KEY in each.
  Run `ssheep master flock "<name>"` again for a second one.
    ssheep flock list            every flock this machine knows, and its role in each
    ssheep see                   every flock, live
    ssheep see "myflock"         one flock
    ssheep run "myflock" -- CMD  run in one flock
  A machine can be a sheep in one flock and a connector in another. A relay and a
  connector can serve several flocks at once: one reachable machine, one port. Each
  flock is entirely separate — its own key, roster, connectors and machine names —
  so being in a second flock cannot leak anything into the first.

SHELL
  ssheep shell <flock> --name NAME            an interactive terminal on one machine
  ssheep shell <flock> --name NAME -- CMD...  one command, with a terminal
  A REAL ssh session — pty, window size, ^C, colours, exit status — but the ssh
  server runs INSIDE the encrypted tunnel, not on a port:
  - no sshd installed on the machine, no authorized_keys, no known_hosts, no
    first-use trust, nothing listening. The machine is whoever the signed roster
    says it is, and the flock key is what proves it.
  - ssh's own authentication is deliberately off, because the tunnel already
    answered who is asking: only a roster-listed master can complete the
    handshake at all. The ssh host key is invented per connection and thrown away,
    and the client does not check it — the tunnel is the trust anchor, not a host
    key, and a second, weaker check would be worse than none.
  - the shell runs as the user the agent runs as. Run the agent as yourself (a
    systemd user unit is the tidy way) and a shell here is your own environment.
  - no terminal asked for, none given: piping a command through gets the bytes
    exactly as written, with no terminal line endings and no echo.
  - exit status is passed back out the way ssh does.
  Linux and macOS only, because it needs a pty. No file transfer, no port
  forwarding, no agent forwarding, no subsystems: sessions are all it serves.

MULTIPLE MASTERS
  A master ticket is the only one that carries the flock key, so the machine that takes it can
  add and remove machines, mint tickets and accept a connector's offer — exactly as
  the first master does. `--masters 0` mints none.
  - A master has no service: it connects when you run a command. As it connects it
    asks the connector for the current roster and adopts it when it is newer, under
    the same rules a sheep uses, so a master that has been away still sees machines
    added since.
  - The cost is real: the flock key then exists in two places. Mint as few master
    tickets as you can bear, and treat each line as being as sensitive as the master.

STATE
  Everything lives under $SSHEEP_DIR, default ~/.ssheep, one directory per flock:
    ~/.ssheep/flocks/<name>/flock.key.json   the flock key. SENSITIVE. Off the connector.
                                             Present only where a master ticket put it.
    ~/.ssheep/flocks/<name>/node.key.json    this machine's identity in that flock. SENSITIVE.
    ~/.ssheep/flocks/<name>/roster.json      the signed roster. Public; safe to share.
  Once enrolled, a machine needs no arguments: `ssheep sheep` and
  `ssheep connector` know what they are — and which flocks they are for.
  (The old `--dir <path>` flag still works; it now just sets $SSHEEP_DIR.)

ROLES
  master     holds a flock key, mints tickets, sends commands. More than one is
             fine: a master ticket carries the flock key, so any master can add and
             remove machines. Keep master lines as safe as the master machine.
  sheep      runs the agent, executes commands
  connector  blind relay + address book; also a member, which is how it tells the
             flock where it is. The only role needing a reachable address.
  One binary does all three; the role is a subcommand, or read from the ticket.

COMMANDS
  ssheep master [flock] <name> [--relay H:PORT] [--private] [--sheep N]
                [--connector N] [--masters N] [--invite] [--watch 3m]
                                          set up a flock; prints the lines to paste
  ssheep join "<ticket>"                  take a ticket: install it, then be what it
                                          says (sheep and connector serve; master
                                          installs and reports). --install-only to
                                          take it and stop
  ssheep sheep "<ticket>"                 same, when you know it is a sheep
  ssheep connector "<ticket>"             same, for a connector (--addr H:PORT,
                                          --port N, --public)
  ssheep see [<flock>]                    the flocks, live (all of them by default)
  ssheep run <flock> -- CMD...            every sheep in one flock
  ssheep run <flock> --name NAME -- CMD... one machine
  ssheep shell <flock> --name NAME        an interactive terminal on one machine,
                                          with or without -- CMD (Linux, macOS)
  ssheep forget <flock> --name NAME       revoke a machine
  ssheep flock list                       the flocks this machine knows

  step by step, when you want control:
  ssheep invite <flock> --name N [--role R]  mint one ticket (roles: sheep, connector, master)
  ssheep connector                        run a relay with no flock of its own
  ssheep connector add|remove|list        manage a flock's connectors by hand
  ssheep pin --addr H:PORT                print a connector's fingerprint

EXIT CODES AND OUTPUT
  run exits non-zero when a command fails, and prints "<machine>: exited with status N".
  A machine that is revoked stops with "this machine is no longer in the flock".

GOTCHAS WORTH KNOWING
  - A new flock starts with the project's public relay (relay.ssheep.xyz:7000)
    already in its roster, so it works before you have run a connector of your
    own. Use --private to have none.
  - A connector works out what address it is at by asking the flock what it looks
    like from outside. Behind a NAT with no port forwarding that guess is wrong;
    the master will say so, and --addr is there to be told the truth.
  - More than one connector is worth doing: machines try them in roster order and
    survive losing any of them. A single connector is a single point of failure.
  - Online/offline is reported PER CONNECTOR. With several connectors, a machine
    connected to a different one can show as offline.
  - A connector serves only the flock it was given unless started with --public.
  - A machine in two flocks needs the ticket for EACH; it does not reuse an
    identity across flocks, by design.
  - Revocation is enforced by connectors; a machine already in a direct conversation
    is not interrupted until it reconnects.
  - Changing a relay's certificate strands its members: they pin the fingerprint
    and cannot fetch the roster that would tell them the new one.
  - No interactive shell or file transfer yet. run executes and streams output.

WHAT IT IS NOT
  - Not audited. Not hardened. Assume bugs.
  - No accounts, no telemetry, no SaaS. Nothing phones home.
  - Not affiliated with any other project; it is ~4k lines of Go, standard library only.
