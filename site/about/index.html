ssheep  /  how it works

How it works

Short version: a signed file, a key, and a blind relay. One binary, three roles, as many flocks as you like.

Very early. Not secure. A working prototype, not an audited tool. The protocol will change. Do not use it for anything you would be upset to lose.

One command, then one line per machine

ssheep master flock "myflock" creates the flock, pre-adds the project's public relay, and prints one line per machine — a sheep, a connector, and a spare master. Each line installs the binary and joins, and the ticket says what the machine is to be, so there is no verb to get wrong:

curl -fsSL https://ssheep.xyz/install.sh | sh -s -- --ticket "<ticket>"

The installer does the joining itself, by the full path it just wrote to, so it works whether or not that directory happens to be on PATH.

The three roles

👑 masterHolds a flock's key, mints tickets, sends commands. Needs no reachable address, so it can be a laptop that is usually off.
🐑 sheepA managed machine. Dials out and keeps the connection open. Holds only its own private key.
📡 connectorA directory and a relay, and a member of the flock like anything else. The only machine that needs a reachable address — and it can be any machine.

It is one binary. The role is just the subcommand you run. A machine can hold different roles in different flocks.

What keeps it safe

The roster is a file, and it is public

It lists who is in the flock and their public keys, and it is signed by the flock key. Every member holds a copy, so there is no database to back up and no server to restore. Keep it in git and you have an audit trail of every machine ever added.

The only secret is the flock key

It signs rosters, so it is needed to add or remove a machine — and for nothing else. Keep it offline, and never on a connector.

Peers verify each other, not the relay

A connector checks that a connecting machine holds the key the roster says it holds, and then forwards opaque payloads. Master and sheep agree on an encryption key between themselves, using ephemeral keys signed by their permanent ones. The relay sees ciphertext it can neither read nor forge.

The connector can

✓see which machines are talking, when, and what they are called
✓route between them, and say who is not welcome

The connector cannot

✗read a command or its output, forge one, or impersonate anyone
✗add itself to the flock, or accept a roster signed by anything but the flock key

Many flocks, one machine

A machine is not tied to one flock. Run ssheep master twice and you hold two flocks; hand a machine two tickets and it serves both. Each flock is entirely its own: its own key, its own roster, its own connectors, its own name for the machine. Nothing is shared between them, so being in a second flock cannot leak anything into the first.

This is why a machine holds a separate key in every flock. A ticket is minted before the machine it is meant for has ever been spoken to, so the key has to come from the ticket — and one key per flock means the same box looks like a different machine to each one. Everything lives in ~/.ssheep/flocks/<name>/.

ssheep master flock "home"     # a second flock, on the same machine
ssheep master flock "work"
ssheep flock list              # every flock this machine knows

A relay can serve many flocks at once, and a connector can be a connector for several at the same time. One reachable machine, one port, many flocks.

More than one master

The flock key is the authority — it signs the roster, so whoever holds it can add and remove machines. Keeping it in one place is tidy and fragile: a flock whose key lives on one laptop cannot be changed the day that laptop dies. So a master ticket carries the flock key, and one is minted by default. A second master can mint tickets, revoke machines and send commands exactly as the first one does.

A master is not a service: it connects when you type a command. So it asks the connector for the current roster as it connects and takes it when it is newer — that is how a master that has been away for weeks still knows about machines added since.

The cost, plainly: the key now exists in two places. Mint as few master tickets as you can bear, and keep each one at least as safe as the machine you run ssheep from.

How a connector finds its own address

A master cannot know a connector's address in advance — the connector is the machine with the public address, and the master has never spoken to it. So the connector says so itself: it asks the flock what it looks like from outside, and offers itself at that address on its listening port, through whatever connector the flock already has.

Three things have to line up before the offer is believed, and the middle one is the point: the roster must list that machine as a connector — only the master can do that — the offer must be signed by that machine, so the relay that carried it could not have rewritten the address and promoted itself, and the address must answer with exactly the certificate the offer claims.

If the guess is wrong, the master says so and adds nothing, and --addr is there to be told the truth.

Adding and removing machines

ssheep master generates a key pair for each new machine, adds its public key to the roster, re-signs it, and prints a ticket. The printed line installs the binary and joins in one command, and the ticket says what the machine is to be — a sheep, a connector, or another master. The ticket carries that machine's private key, so hand it over privately. ssheep forget --name sheep-2 removes one and publishes the new roster; connectors drop it within seconds.

More than one connector

A single connector is a single point of failure, which is a strange thing for a tool whose point is not needing anyone. A flock can list several: every sheep keeps a link to each of them, and a master tries them in order. Losing one costs the flock nothing. A new flock starts with the project's public relay already listed, so it works before its owner has run a connector of their own.

What is missing

Direct peer-to-peer connections, an interactive shell, and file transfer. Today every byte goes through a connector, and run executes a command and streams its output back. Online and offline is reported per connector, so with several connectors a machine connected to a different one can look offline. The relay path is the floor; direct connections would sit on top of it rather than replace it.
