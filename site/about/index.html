ssheep  /  how it works

How it works

Short version: a signed file, a key, and a blind relay. One binary, three roles, as many flocks as you like.

Very early. Not secure. A working prototype, not an audited tool. The protocol will change. Do not use it for anything you would be upset to lose.

One command, then one line per machine

ssheep master flock "myflock" creates the flock, pre-adds the project's public relay, and prints one line per machine — three sheep and a spare master. Each line installs the binary and joins, and the ticket says what the machine is to be, so there is no verb to get wrong:

curl -fsSL https://ssheep.xyz/install.sh | sh -s -- --ticket "<ticket>"

The installer does the joining itself, by the full path it just wrote to, so it works whether or not that directory happens to be on PATH.

The roles

👑 masterHolds a flock's key, mints tickets, sends commands. Needs no reachable address, so it can be a laptop that is usually off.
🐑 sheepA managed machine. Dials out and keeps the connection open. Holds only its own private key.
📡 relayA sheep that happens to be reachable. It runs the relay itself and offers itself to the flock, so nobody has to pick one — the machines that can be reached help, and the rest simply stay sheep.

It is one binary. The role is just the subcommand you run, and a machine can hold different roles in different flocks.

What keeps it safe

The roster is a file, and it is public

It lists who is in the flock and their public keys, and it is signed by the flock key. Every member holds a copy, so there is no database to back up and no server to restore. Keep it in git and you have an audit trail of every machine ever added.

The only secret is the flock key

It signs rosters, so it is needed to add or remove a machine — and for nothing else. Keep it offline, and never on a connector.

Peers verify each other, not the relay

A relay checks that a connecting machine holds the key the roster says it holds, and then forwards opaque payloads. Master and sheep agree on an encryption key between themselves, using ephemeral keys signed by their permanent ones. The relay sees ciphertext it can neither read nor forge.

The relay can

✓see which machines are talking, when, and what they are called
✓route between them, and say who is not welcome

The relay cannot

✗read a command or its output, forge one, or impersonate anyone
✗add itself to the flock, or accept a roster signed by anything but the flock key

Many flocks, one machine

A machine is not tied to one flock. Run ssheep master twice and you hold two flocks; hand a machine two tickets and it serves both. Each flock is entirely its own: its own key, its own roster, its own relays, its own name for the machine. Nothing is shared between them, so being in a second flock cannot leak anything into the first.

This is why a machine holds a separate key in every flock. A ticket is minted before the machine it is meant for has ever been spoken to, so the key has to come from the ticket — and one key per flock means the same box looks like a different machine to each one. Everything lives in ~/.ssheep/flocks/<name>/.

ssheep master flock "home"     # a second flock, on the same machine
ssheep master flock "work"
ssheep flock list              # every flock this machine knows

One relay can serve many flocks at once, so one reachable machine — one port — can carry several flocks at the same time.

More than one master

The flock key is the authority — it signs the roster, so whoever holds it can add and remove machines. Keeping it in one place is tidy and fragile: a flock whose key lives on one laptop cannot be changed the day that laptop dies. So a master ticket carries the flock key, and one is minted by default. A second master can mint tickets, revoke machines and send commands exactly as the first one does.

A master is not a service: it connects when you type a command. So it asks the connector for the current roster as it connects and takes it when it is newer — that is how a master that has been away for weeks still knows about machines added since.

The cost, plainly: the key now exists in two places. Mint as few master tickets as you can bear, and keep each one at least as safe as the machine you run ssheep from.

A shell on any machine

ssheep shell "myflock" --name pi puts a terminal on one machine, and … -- htop runs one command with a terminal. It is a real ssh session — the window size, ^C, colours and exit status all work — but the ssh server runs inside the encrypted tunnel rather than on a port.

That is where the unusual part is: there is no sshd to install on the machine, no authorized_keys to copy, no known_hosts and no first-use trust, and nothing listening. The machine is whoever the signed roster says it is, and the flock key is what proves it — which is also why ssh's own authentication is switched off: the tunnel already asked who is calling, and only a master can get that far.

The shell runs as the user the agent runs as, so run the agent as yourself — a systemd user unit is the tidy way — and a shell here is your own environment, dotfiles and all. Linux and macOS only, since it needs a pty.

How a machine becomes the relay

A master cannot know a relay's address in advance — the relay is the machine with the public address, and the master has never spoken to it. So the machine says so itself: every machine asks the flock what it looks like from outside, works out every address it might be reachable at, and offers itself on the connection it already holds to each relay in the flock.

Four things have to line up before the offer is believed. The roster must say that machine may relay — every ticket grants it, and only the master can open that gate. The offer must be signed by that machine, so the relay that carried it could not have rewritten the address and promoted itself. The address must answer with exactly the certificate the offer claims. And the machine must not already be relaying, so a machine that offers several addresses is counted once.

Every address is offered and the first that answers wins, so nobody has to work out which machine has a public address. If none answers — a machine behind a NAT with no port forwarding, or a closed port — the master says so and adds nothing, and the machine stays a sheep. --addr is there to be told the truth when the guess is wrong.

Adding and removing machines

ssheep master generates a key pair for each new machine, adds its public key to the roster, re-signs it, and prints a ticket. The printed line installs the binary and joins in one command, and the ticket says what the machine is to be — a sheep, a dedicated relay, or another master. The ticket carries that machine's private key, so hand it over privately. ssheep forget --name sheep-2 removes one and publishes the new roster; relays drop it within seconds.

More than one relay

A single relay is a single point of failure, which is a strange thing for a tool whose point is not needing anyone. So a flock keeps a handful: every machine keeps a link to each of them, and a master tries them in order. Losing one costs the flock nothing, and see asks every relay and merges the answers, so "online" is a fact about the flock rather than about whichever relay replied. A new flock starts with the project's public relay already listed, so it works before its owner has a reachable machine of their own — and as machines join, the ones that can be reached take over the relaying.

What is missing

File transfer and port forwarding, and direct peer-to-peer connections. Today every byte goes through a relay, and run executes a command and streams its output back. A machine behind a NAT with no port forwarding and no IPv6 cannot relay yet; UPnP and hole punching would sit on top of the relay rather than replace it. The relay path is the floor.
